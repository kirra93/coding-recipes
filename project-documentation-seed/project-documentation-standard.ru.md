# Стандарт проектной документации

> Статус: заготовка
> Аудитория: сопровождающие проект, инженеры и coding agents
> Область: документация репозитория без привязки к стеку
> Канонический язык: выберите один для каждого репозитория; для инженерных
> источников истины рекомендуется английский

## 1. Цель

Документация должна помогать инженеру быстро ответить на пять вопросов:

1. Что это за проект и как его запустить?
2. Каковы его текущие границы и инварианты?
3. Почему были приняты долговечные решения?
4. Какая работа активна и как проверить её результат?
5. Как диагностировать проблему и восстановить систему?

Лучше иметь небольшой связанный набор достоверных документов, чем большую
коллекцию заметок. У каждого правила или факта должен быть один канонический
источник; остальные документы ссылаются на него, а не копируют содержание.

## 2. Порядок начального оформления

Создавайте документацию в таком порядке:

1. `README.md` — входная точка для человека и рабочий quickstart.
2. `AGENTS.md` — краткие инструкции и маршрутизация по источникам истины для
   coding agents.
3. `docs/INDEX.md` — карта документации.
4. `docs/architecture/overview.md` — текущие границы системы и направление
   зависимостей.
5. `docs/standards/` — только реально действующие правила проекта.
6. `docs/runbooks/local-development.md` — когда настройка, тестирование на
   устройствах, сервисы, конфигурация, восстановление или deployment уже не
   помещаются в короткий README.
7. Добавляйте ADR, Tasks, контракты и другие документы только по мере появления
   реальной потребности.

Не создавайте пустые папки и спекулятивные документы только ради полного дерева
из примера ниже.

## 3. Файлы в корне

### `README.md`

README предназначен для нового участника команды. Он должен быть коротким и
исполняемым:

- назначение проекта и его текущая зрелость;
- необходимые инструменты;
- установка и локальный запуск;
- необходимая конфигурация без реальных секретов;
- команды тестов, линтинга и сборки;
- команды остановки, только если локальным сервисам требуется явная процедура
  завершения работы;
- ссылки на `AGENTS.md` и `docs/INDEX.md`;
- самая частая проблема запуска или ссылка на соответствующий runbook.

Не превращайте README в историю архитектуры, полную спецификацию API или
операционное руководство.

### `AGENTS.md`

`AGENTS.md` — документ маршрутизации и рабочих правил, а не копия архитектуры
или code style. Он должен содержать:

- обязательное чтение и приоритет инструкций;
- назначение проекта, долговечные границы и явные non-goals;
- небольшой набор общих правил работы;
- ссылки на канонические документы по архитектуре, стилю, тестированию,
  документации и эксплуатации;
- точные точки входа для проверок;
- правила работы с архивом и контекстом;
- обязательное содержание итогового handoff.

Дополнительные `AGENTS.md` размещайте только в пакетах или модулях, которым
нужны более специфичные правила. Вложенный файл расширяет или переопределяет
корневую политику для своего поддерева. Не повторяйте неизменённые общие правила.

Меняющиеся приоритеты храните в Roadmap или активных Tasks. Не превращайте
`AGENTS.md` в живой backlog.

Копируемый skeleton:

````markdown
# Инструкции для агентов проекта <Project>

## Обязательное чтение

Перед изменением кода прочитайте:

1. `docs/architecture/overview.md`;
2. относящиеся к задаче стандарты проекта;
3. ближайшие ADR, Task, контракт, код и тесты.

Следуйте ближайшему применимому `AGENTS.md`. Не определяйте текущую архитектуру
по промптам, архивным Tasks или superseded-документам.

## Область проекта

Назначение: <один конкретный абзац>.

Вне scope без явного запроса:

- <non-goal>.

## Правила работы

- Изучите существующее поведение до редактирования.
- Предпочитайте минимальное целостное изменение.
- Сохраняйте несвязанные изменения рабочего дерева.
- Поддерживайте согласованность кода, тестов, контрактов и документации.
- Не добавляйте зависимости, не коммитьте, не пушьте и не выполняйте
  разрушительные операции без требуемого в проекте разрешения.

## Источники истины

- Архитектура: `docs/architecture/overview.md`.
- Code style: `docs/standards/<code-style>.md`.
- Тестирование: `docs/standards/testing.md`.
- Документация: `docs/standards/documentation.md`.
- Локальная эксплуатация: `docs/runbooks/local-development.md`.

Не дублируйте здесь подробные правила из этих документов.

## Проверка

Сначала запускайте самую узкую подходящую проверку:

```text
<команда тестов проекта>
<команда линтинга проекта>
<полная quality-команда проекта>
```

Не ослабляйте quality gates ради прохождения изменения.

## Архив документации

Считайте каждую папку `archive/` в документации историей, а не текущим
руководством. Открывайте конкретный архивный документ только когда задача явно
требует известный исторический контекст.

## Handoff

Укажите изменённое поведение, принятые решения, выполненные и невыполненные
проверки, обновлённую документацию, оставшиеся риски и дальнейшую работу.
````

## 4. Рекомендуемое дерево документации

```text
docs/
├── INDEX.md                    # обязательная карта
├── architecture/              # текущая структура и границы
│   └── overview.md
├── adr/                       # история долговечных решений
│   └── README.md
├── product/                   # опциональный продуктовый контекст и требования
├── roadmap/                   # опциональные результаты и этапы
├── tasks/                     # ограниченные единицы реализации
│   ├── README.md
│   └── archive/               # история; исключена из обычного поиска
├── contracts/                 # опциональные API, события, схемы, совместимость
├── runbooks/                  # исполняемая эксплуатация и восстановление
└── standards/                 # общие правила репозитория
    └── templates/             # поддерживаемые копируемые шаблоны
```

Используйте доменные подпапки, когда раздел разрастается, например
`architecture/catalog/` или `runbooks/payments/`. Не повторяйте структуру
исходного кода механически.

## 5. Что куда относится

| Раздел | На какой вопрос отвечает | Чем не должен становиться |
|---|---|---|
| `architecture/` | Как сейчас работает система и кто чем владеет? | Планом будущего или дневником решений |
| `adr/` | Почему долговечное решение выбрали среди альтернатив? | Чек-листом реализации |
| `product/` | Какая проблема, результат пользователя и scope важны? | Технической архитектурой |
| `roadmap/` | Какие результаты следуют дальше и почему в таком порядке? | Подробным backlog Tasks |
| `tasks/` | Какой ограниченный результат будет реализован и проверен? | Постоянным источником архитектуры |
| `contracts/` | Чем обмениваются потребители и поставщики? | Внутренними заметками реализации |
| `runbooks/` | Как безопасно управлять или восстанавливать систему? | Концептуальным обзором |
| `standards/` | Какие общие правила репозитория реально действуют? | Общими советами без влияния на проект |

Используйте Task как единицу реализации в репозитории. Если команда работает
календарными спринтами, ведите расписание ровно в одном месте: либо в Roadmap
репозитория, либо во внешней системе управления проектом. Связывайте элементы
расписания с Tasks и не поддерживайте дублирующие спецификации в `tasks/` и
`sprints/`.

Не создавайте Task для каждого небольшого изменения. Он нужен, когда работа
проходит в несколько этапов либо меняет архитектуру, контракты, persistence,
эксплуатацию или существенный пользовательский сценарий. Узкое исправление
может быть задокументировано кодом, тестами и его commit или pull request.

## 6. D.O.C.S. как проверка релевантности

Для каждой нетривиальной фичи или этапа сохраняйте применимые знания D.O.C.S.:

1. **Design Decisions** — выбранное решение, отвергнутые альтернативы, причины,
   компромиссы и совместимость.
2. **Operational Context** — окружение, имена конфигурации и секретов,
   зависимости, порты, deployment и runtime-ограничения.
3. **Code Understanding** — неочевидные data flow, lifecycle, алгоритмы,
   инварианты, обработка ошибок и fallback-маршруты.
4. **Support Information** — симптомы, причины, диагностика, восстановление,
   rollback, backfill и проверка.

Это чек-лист, а не четыре обязательных заголовка. Небольшому Task может не
понадобиться ни одного блока или достаточно одного. Удаляйте нерелевантные
разделы вместо заполнения водой.

Помещайте информацию в наиболее долговечный источник: решение — в ADR, текущие
границы — в Architecture, команды — в Runbook, а в Task — только специфичные
детали выполнения.

## 7. Метаданные документов

Каждый поддерживаемый документ одного из перечисленных ниже типов должен
начинаться с соответствующих его типу метаданных. `README.md`, `AGENTS.md`,
`docs/INDEX.md` и шаблоны — исключения. Архивные и superseded-документы
сохраняют метаданные, но не являются текущими источниками истины.

Общие метаданные:

```markdown
# <Заголовок>

> Status: <статус для соответствующего типа>  
> Owner: <команда, модуль или роль>  
> Last reviewed: YYYY-MM-DD  
> Canonical for: <точная область>  
> Related: [Document](relative/path.md), [ADR](../adr/0001-example.md)
```

Используйте статусы, соответствующие типу документа:

| Документ | Статусы |
|---|---|
| Architecture | `draft`, `active`, `superseded`, `archived` |
| ADR | `proposed`, `accepted`, `rejected`, `superseded` |
| Task | `planned`, `active`, `blocked`, `completed`, `cancelled`, `archived` |
| Roadmap | `draft`, `active`, `superseded` |
| Runbook | `draft`, `active`, `deprecated` |
| Contract | `draft`, `active`, `deprecated`, `superseded` |
| Standard | `draft`, `active`, `superseded` |

Не указывайте `Related`, если полезной связи нет. Неканонический рабочий
документ должен указывать владеющий им Task или расположение в архиве, а не
претендовать на статус источника истины.

Используйте lowercase kebab-case для имён файлов и числовые префиксы для
упорядоченных ADR и Tasks. Избегайте `notes.md`, `final-v2.md`, `new-plan.md` и
дат, не являющихся частью темы.

`Last reviewed` означает проверку содержимого на соответствие реальности, а не
исправление пунктуации.

## 8. Шаблоны

Храните копируемые шаблоны в `docs/standards/templates/`, отдельно от текста
стандарта. Рекомендуемые шаблоны:

- `architecture.md`;
- `adr.md`;
- `task.md`;
- `runbook.md`;
- шаблоны контрактов или миграций — только если проект регулярно их использует.

Помечайте разделы шаблона как:

- `Required` — всегда заполнить конкретным содержанием;
- `Optional` — удалить, если он ничего не добавляет;
- `Conditional` — обязателен только при указанном условии.

После копирования удаляйте инструкции, неиспользуемые заголовки и placeholders.
Не добавляйте повсюду `Not applicable` только ради визуально полного шаблона.

## 9. Жизненный цикл и архивы

- Architecture описывает текущую реальность и меняется вместе с системой.
- Принятый ADR неизменяем, кроме уточнений; изменившееся решение оформляется
  новым ADR, который supersedes предыдущий.
- Task может уточняться во время выполнения, затем фиксирует результат перед
  архивацией.
- Runbook обновляется и перепроверяется при изменении команд или runtime.
- Статус Roadmap меняется по мере достижения результатов, но завершённая история
  остаётся краткой.

Папка `archive/` — историческое хранилище:

- исключайте её из обычного поиска, контекста агентов, планирования и индексов;
- открывайте только конкретный известный файл ради явного исторического вопроса;
- помечайте архивные документы как неактуальные источники истины;
- при наличии замены ссылайтесь на активный документ;
- никогда не используйте отменённую работу как текущее руководство.

## 10. Процесс изменения

Когда меняется поведение:

1. до реализации определите затронутые канонические документы;
2. обновите код, тесты, контракты и документацию одним целостным изменением;
3. добавляйте ADR только для долговечного выбора с реальными альтернативами;
4. по возможности проверяйте команды и примеры;
5. меняйте `Last reviewed` только у действительно проверенных документов;
6. обновляйте `docs/INDEX.md`, когда меняется навигация;
7. укажите изменения документации и пробелы в итоговом handoff.

Документация является частью definition of done, если меняются установка,
поведение, контракты, архитектура, persistence, эксплуатация или поддержка.

## 11. Язык и переводы

Выберите один канонический инженерный язык на репозиторий. Если переводы нужны:

- явно отметьте канонический файл;
- свяжите переводы ссылками с ним;
- используйте парные имена, например `overview.en.md` и `overview.ru.md`;
- обновляйте обе версии одним изменением или помечайте перевод устаревшим;
- не допускайте появления двух независимых источников истины на разных языках.

## 12. Комментарии в коде и генерируемые справочники

Используйте нативные для стека комментарии для публичных контрактов,
неочевидных инвариантов, side effects, retry/concurrency и границ интеграций.
Объясняйте причины, а не пересказывайте очевидный код.

Предпочитайте генерируемые OpenAPI, schema или CLI-справочники, если код может
надёжно их создать. В рукописной документации оставляйте семантику, примеры,
решения и operational context, которые генератор объяснить не может.

Явно помечайте сгенерированные файлы, документируйте команду их генерации и не
редактируйте их вручную.

## 13. Чек-лист ревью

- Есть ли ровно один текущий источник истины для каждого правила?
- Описывает ли Architecture текущее, а не желаемое поведение?
- Сохраняют ли ADR причины, не превращаясь в планы реализации?
- Ограничен ли каждый активный Task, проверяем ли он и связаны ли зависимости?
- Может ли новый инженер выполнить Runbook без скрытых знаний?
- Актуальны ли команды, имена env-переменных, порты и примеры?
- Исключены ли архивные и superseded-документы из обычного руководства?
- Работают ли ссылки и показывает ли `docs/INDEX.md` важные точки входа?
- Объясняют ли комментарии и docs то, что нельзя выразить одним кодом?
- Можно ли удалить какой-либо документ или раздел без потери полезных знаний?

## 14. Типовые ошибки

- `AGENTS.md` повторяет всю архитектуру и устаревает.
- README, Task и Architecture формулируют одно правило по-разному.
- Планируемая архитектура представлена как уже реализованная.
- Tasks и sprints дублируют одну спецификацию реализации.
- Принятые ADR незаметно переписываются, уничтожая историю решений.
- Каждый заголовок шаблона заполнен бессмысленным `Not applicable`.
- Архивы индексируются или автоматически загружаются как текущий контекст.
- Команды и примеры конфигурации никогда не проверяются.
- Временные заметки с именами вроде `final-v3-really-final.md` становятся
  случайными источниками истины.

Обычно помогает консолидация: выберите канонический документ, обновите его,
замените дубли ссылками, а устаревшие материалы архивируйте или удалите.
