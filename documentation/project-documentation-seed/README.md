# Как начать проект с документацией и Codex

Сначала опишите, что хотите сделать и какие ограничения уже известны. Затем дайте Codex этот документ и стандарт: он поможет разобрать требования, выбрать решения и собрать первый рабочий сценарий.

## 1. Положить стандарт в проект

В новом репозитории создайте два файла:

```text
docs/
├── standards/
│   └── documentation.md
└── product/
    └── initial-product.md
```

В `docs/standards/documentation.md` скопируйте [русскую версию стандарта](project-documentation-standard.ru.md). Если у вас уже есть свои правила по коду, тестам или стеку, положите их рядом в `docs/standards/`.

Адаптируйте скопированный стандарт: выберите язык документации, укажите владельца, уберите ссылки на перевод, которого в проекте нет. При принятии правил поменяйте `status: seed` на `active`; дату ревизии ставьте после проверки. Для проекта с документацией на русском можно выбрать русский каноническим языком.

В этом наборе [английская версия](project-documentation-standard.en.md) остаётся оригиналом, русская — переводом. В своём проекте поддерживайте одну выбранную версию правил. Шаблоны конкретного проекта, когда понадобятся, храните в `docs/standards/templates/`.

## 2. Описать продукт

Заполните `docs/product/initial-product.md` своими словами. Опишите продукт целиком, но явно отделите первую версию от того, что хотите добавить потом. «Полное описание» не означает, что всё нужно реализовать за один заход.

Можно начать с такого каркаса:

```markdown
# Описание продукта

## Что делаем и для кого
Какую проблему решаем, кто пользуется продуктом, какой результат получает.

## Пользовательские сценарии
Кто что делает, что вводит и что получает. Примеры от начала до конца.

## Функции
Для каждой: поведение, входные данные, результат, ошибки и ограничения.
Отметить: MVP / после MVP / пока под вопросом.

## Данные и доступ
Какие сущности храним, как они связаны, кто что может читать и менять.
Что происходит при удалении, повторной операции или конфликте изменений.

## Интеграции
Внешние сервисы, API, импорт и экспорт. Что делать, если сервис недоступен.

## Требования к работе системы
Ожидаемая нагрузка, задержки, безопасность, приватность, доступность.
Где возможно — конкретные числа и условия проверки.

## Стек и окружение
Обязательные язык, версии, фреймворки, БД, ОС, способ запуска и размещения.
Отдельно: предпочтения, по которым Codex может предложить другой вариант.

## Ограничения архитектуры
Уже принятые границы, зависимости и требования с объяснением причин.
Если решение ещё не принято — прямо так и написать.

## Что не делаем
Что точно не входит в первую версию и в этот проект.

## Как поймём, что MVP готов
Проверяемые сценарии: действие пользователя → ожидаемый результат.

## Открытые вопросы
Что пока неизвестно и что нельзя решать без обсуждения.
```

Не пишите просто «быстро», «надёжно» или «чистая архитектура». Лучше: «повторный запрос не создаёт второй заказ», «первый релиз работает на одном сервере», «внешний API может быть недоступен до минуты». Если ограничений по архитектуре нет, не нужно заранее требовать микросервисы или сложный набор слоёв.

## 3. Дать Codex первый промпт

Откройте корень проекта в VS Code и отправьте в панель Codex:

```text
Начинаем проект. Документацию ведём на русском.

Прочитай docs/product/initial-product.md и
docs/standards/documentation.md, а также имеющиеся AGENTS.md
и относящиеся к задаче стандарты. Проверь, есть ли уже код и настройки.

Сначала разберём требования. Код и файлы пока не меняй.
1. Кратко опиши продукт, границы MVP и критерии готовности.
2. Найди противоречия и вопросы, которые меняют реализацию.
   Не выдумывай ответы; некритичные допущения явно перечисли.
3. Предложи стек и минимальную архитектуру под эти требования.
   Соблюдай обязательные ограничения, предпочтения можно обсуждать.
   Для спорных решений объясни выбор и компромиссы.
4. Предложи первый небольшой сценарий, который можно реализовать
   целиком, запустить локально и проверить.
5. Дай короткий порядок работы и способ проверки результата.

Если репозиторий уже содержит реализацию, учитывай её и не предлагай
пересоздавать проект без конкретной причины.
Дождись моих ответов и согласования решений перед изменением файлов.
```

Ответьте на вопросы, поправьте границы MVP и согласуйте первый сценарий. Если описание поменялось, обновите исходный документ до начала реализации.

## 4. Начать реализацию

Когда решения понятны, отправьте второй промпт:

```text
Решения выше согласованы. Обнови initial-product.md по нашим уточнениям.
Оформи минимальную документацию по docs/standards/documentation.md:
README.md, AGENTS.md, docs/INDEX.md и docs/architecture/overview.md.

В документах отделяй согласованные планы от уже реализованного.
Продуктовые требования храни в docs/product/, принятую архитектуру —
в overview.md, причины существенных решений — в ADR, когда он нужен.
Не дублируй подробные правила в AGENTS.md; оставь ссылки.
Не создавай пустые документы и каталоги ради структуры.

Затем создай минимальный проект и реализуй согласованный первый
сценарий целиком. Сохрани существующий код и несвязанные изменения.
Добавь необходимые проверки, запусти их и проверь локальный запуск.
Укажи в README реальные команды установки, запуска и проверки.
Обнови документацию по фактическому результату.

В конце покажи, что работает, что проверено и что ещё не реализовано.
Не коммить и не пушь.
```

После старта `initial-product.md` остаётся исходным описанием. Если выделили из него поддерживаемые требования и ограничения в другие документы, замените соответствующие разделы ссылками. Текущую архитектуру сверяйте с `docs/architecture/overview.md` и кодом; оставшиеся идеи не должны выглядеть как реализованное поведение.

Дальше двигайтесь по одному сценарию. Для крупной задачи можно завести Task по стандарту; для небольшой правки достаточно понятного запроса и проверки.

## 5. Проверить и закоммитить

Перед первым коммитом запустите проект по README и проверьте выбранный сценарий. Убедитесь, что команды проверок выполняются, в документах нет придуманных возможностей, а в diff — секретов и локальных дампов.

Посмотрите `git status` и `git diff`, добавьте в индекс только нужные файлы и проверьте `git diff --cached`. После этого можно коммитить. Если коммит делает Codex, отдельного запроса достаточно:

```text
Проверь diff и создай коммит с изменениями по этой задаче.
Не включай посторонние изменения, секреты и локальные артефакты.
Покажи сообщение и хеш коммита. Не пушь.
```
